# API request validation and error responses

Every API route that takes a body reads it through one shared guard (`Validation/RequestBody.cs`), and every route runs inside one shared failure mapper (`Validation/RouteFailures.cs`). Each entity has one validator (`Validation/EntityValidators.cs`), and its create and update routes both call it, so the two cannot drift apart. Error bodies are short plain strings. They never contain a stack trace or exception text.

All routes stay `AuthorizationLevel.Anonymous` on purpose: the Static Web App route table enforces the `admin` role in front of this bring-your-own backend.

## Request bodies (every body-reading route, Events included)

| Request | Status | Body |
| --- | --- | --- |
| `Content-Type` present and not `application/json` or a `+json` type (for example `text/plain`) | 415 | `Content-Type must be application/json.` |
| No `Content-Type` header | read as JSON | |
| Empty body, truncated or malformed JSON, wrong JSON shape or value type | 400 | `Request body is empty or malformed.` |
| The JSON literal `null` | 400 | `Request body must not be null.` |

Property names are case-insensitive and camelCase, as before. A `charset` other than UTF-8 is transcoded. The body is read and deserialised once.

The guarded routes are `POST /api/games`, `PUT /api/games/{id}`, `POST /api/themes`, `PUT /api/themes/{id}`, `POST /api/holidays`, `PUT /api/holidays/{id}`, `POST /api/activities`, `PUT /api/activities/{id}`, `POST /api/activities/{id}/comments`, `PUT /api/activities/{id}/comments/{commentId}`, `POST /api/events`, `PUT /api/events/{id}`, `PUT /api/events/{id}/metrics`, `POST /api/series` and `PUT /api/series/{id}`. An update to an id that does not exist is still a 404, checked before the body is read; for the metrics `PUT` that is an unknown Event. For Comments, a `POST` to an Activity that does not exist and a `PUT` of a Comment that does not exist or belongs to another Activity are also 404, checked before the body is read.

## Field rules (400, the message names the field)

| Entity | Field | Rule |
| --- | --- | --- |
| Game, Theme, Holiday, Activity, Event | `Name` | Trimmed, then required and at most 100 characters. The trimmed value is stored. Messages: `Name is required.` / `Name must be 100 characters or fewer.` |
| Game | `Website` | Optional: `null`, empty or whitespace is valid. Otherwise at most 2048 characters (checked first, `Website must be 2048 characters or fewer.`), then an absolute `http` or `https` URI, in any case (`Website must be an http or https address.`). So `ftp://...`, `javascript:...` (in any case, with or without leading spaces), `data:...` and a bare `example.com` are refused. The value is stored as sent, not trimmed (unlike `Name`). The rule (`FieldRules.HttpAddress`) runs only on create and update: a Website stored before it still reads back unchanged, and every save of that Game that still sends it is refused, so renaming an old Game whose Website is not http(s) is blocked until the Website is fixed. The Games editor checks the same rule and message before it sends anything, and shows a stored Website as a link only when it passes. |
| Game | `ImageUrl`, `IconUrl` | Optional, at most 2048 characters. Length only; there is no URL-scheme check. |
| Activity | `Description`, `Rules`, `SetupRequirements` | At most 2000 characters each. The Activity's old single text field is gone (#133): a `comments` value in the body, of any length, is ignored and not stored. A Web build left open across the deploy keeps sending it, and the API ignores it, so text typed into the old editor in that window is lost. An Activity's Comments are rows of their own (below). |
| Activity | `GameId` | Required (`GameId is required.`) and must name an existing Game (`Game not found.`). The Activities editor checks the required rule first, before it sends anything, with its own wording: `Game is required.` |
| Activity | `ThemeIds`, `HolidayIds` | Lenient: a missing or `null` list is stored as `[]`, and duplicates are removed. Whether the ids exist is not checked. |
| Activity | `MinPlayers`, `MaxPlayers`, `DurationMinutes` | Players and duration (#98). Optional (`null` allowed), otherwise a whole number from 1 to 99 for each player count and from 1 to 1440 (24 hours) for the duration, checked in that order after the text fields. The body is read with the Web JSON defaults, which accept a number written as a JSON string: `"maxPlayers":"6"` is read as 6 and stored. A fractional value (`2.5`, `"2.5"`) or a string that is not a whole number (`"six"`) cannot be read into the whole-number field, so it is the malformed-body 400. The body of a `PUT` is the whole Activity, as for every other field: a value it leaves out or sends as `null` is unset. A Web build left open across the deploy does not know these fields and sends a `PUT` without them, so the API clears them: players and duration set on that Activity are lost on that editor's next save. Every Activity route that returns an Activity carries them, `POST /api/activities/{id}/duplicate` copies them, and a row stored before they existed reads back with all three `null` (no migration). A Selection snapshot keeps the values its Activity had when chosen; an older snapshot has none. |
| Event | `Selections` and the rest | Unchanged: the existing `ValidateSelections` messages, run after the name rule. An Occurrence (an Event whose stored row has a `seriesId`, #204) may also have zero Selections; a standalone Event still needs 1 to 5 (`Select between 1 and 5 activities.`). |
| Event | `seriesId`, `occurrenceKey`, `modified` | Set by the API only. A create ignores them (an Event made through `POST /api/events` is always standalone, so a body cannot claim a Series to send zero Selections); an update keeps the stored `seriesId` and `occurrenceKey`, and sets `modified` to true on an Occurrence. A standalone Event's JSON carries none of the three. |
| Series | `Name` | The Event name rule above (trimmed, required, at most 100 characters). Every Occurrence is created with it. |
| Series | `schedule.first` | Required (`Start is required.`). The instant of the first Occurrence with its UTC offset, which is kept: calendar arithmetic runs at that offset (ADR 0002). Its year, at that offset, must be 2000 to 2100 (`Start must be in the years 2000 to 2100.`), so the generator never steps past the last date it can hold. |
| Series | `schedule.rule` | Required (`Repeat must be a known rule.`). `kind` is one of `Weekly`, `BiWeekly`, `MonthlyNthWeekday`, `MonthlySameDate`, `AnnualSameDate`, `AnnualHoliday` (by one name, any case, or by a JSON number); an unknown name is `Repeat must be a known rule.`, and so is a comma list such as `"Weekly,BiWeekly"` or a number written as a string such as `"3"` (the same holds for `week`, `weekday` and `preset`, with their own messages). `MonthlyNthWeekday` needs `week` (`First`, `Second`, `Third`, `Fourth` or `Last`; otherwise `Week of month must be First, Second, Third, Fourth or Last.`) and `weekday` (`Sunday` to `Saturday`; otherwise `Weekday must be a day of the week.`). `AnnualHoliday` needs a known `preset` (otherwise `Holiday preset must be a known preset.`). Stored by name. |
| Series | `schedule.end` | Optional. When set it must be after the start (`End must be after the start.`) and in the years 2000 to 2100 at the offset it is written in (`End must be in the years 2000 to 2100.`); an Occurrence exactly at the end is made, none after it. |
| Series | `slotCount` | 1 to 5 (`Slot count must be from 1 to 5.`). |
| Series | `filters` | Lenient, like an Activity's id lists: `themedOnly`, and `gameIds`, `themeIds`, `holidayIds` stored as `[]` when missing and without duplicates. Whether the ids exist is not checked. Then the three number Filters of the Events page (#95, #98, #232), each stored as the Filter's own setting: `avoidRecent` (how many recent Events to avoid), `playersTonight` and `longestDuration` (minutes). Each is optional (`null` or left out is off), otherwise a whole number from 1 to 10, 1 to 99 (the Activity players limit) and 1 to 1440 (the Activity duration limit), checked in that order after `slotCount`. Messages: `Avoid recent must be a whole number from 1 to 10.` / `Players tonight must be a whole number from 1 to 99.` / `Longest duration must be a whole number from 1 to 1440.` A fractional value is the malformed-body 400. They are left out of the stored and returned JSON while off, so a Series stored before them reads all three as `null` and is written back unchanged (no migration). The body of a `PUT` is the whole Series: one that leaves them out (a client that predates them) turns them off. A "this and following" edit gives the new Series the body's values; the old Series keeps its own. An Occurrence has no Filters of its own. |
| Series | `skipped` | Set by the API only (the keys never to make again: cancelled Occurrences', and the instants an edit would make on a date an Occurrence that stays already holds; ADR 0002); a body's list is ignored on create and edit. |
| Series | `splitAt` | Set by the API only, and left out of the JSON until set: the occurrence key a "this and following" edit split the Series at (see below). A body's value is ignored. |
| Series | `splitFrom` | Set by the API only, and left out of the JSON until set: on the Series a "this and following" edit started, the key it was split from (the old Series' `splitAt`). The instant rather than the old Series' id, because the start rule below needs only the instant and it still holds after the old Series is cancelled. A Series stored before this field reads it as null and has no start limit. A body's value is ignored. |
| Comment | `Text` | Trimmed, then required and at most 1000 characters. The trimmed value is stored. Messages: `Comment text is required.` / `Comment text must be 1000 characters or fewer.` |
| Comment | `EventId` | Optional. On add it must name an existing Event (`Event not found.`), checked after the text rule. An edit never changes it. |
| Event metrics | `Attendees`, `NewAttendees`, `ReturningAttendees` | Optional (`null` allowed), otherwise a whole number from 0 to 1,000,000. Messages: `Attendees must be a whole number from 0 to 1000000.` / `New attendees must be a whole number from 0 to 1000000.` / `Returning attendees must be a whole number from 0 to 1000000.` A fractional or non-numeric count cannot be read into the integer field, so it is the malformed-body 400 (`Request body is empty or malformed.`). |
| Event metrics | `AmountSpent` | Optional (`null` allowed), otherwise 0 to 1,000,000,000 with at most 2 decimal places. Message: `Amount spent must be between 0 and 1000000000 with at most 2 decimal places.` |

Event metrics fields are checked in the order above and the first failing field wins. There is no cross-check between attendees, new and returning. A body with every field `null` is valid and is stored: it clears the values.

The event-create idempotency flow is unchanged: 201 on first insert, 200 on a matching replay, 409 when the details differ, and 400 for a bad `Idempotency-Key` (see `idempotent-event-creates.md`).

## Delete refusal (Games, Themes, Holidays)

A Game, Theme or Holiday that Activities still use cannot be deleted. The route reads every Activity (they all share one partition), counts the ones that use the id, and when that count is above zero answers 409 and deletes nothing. Nothing is cascaded and no id is stripped from an Activity.

| Request | Uses counted | Status | Body |
| --- | --- | --- | --- |
| `DELETE /api/games/{id}` | Activities whose `GameId` is the id | 409 | `This game is used by N activities. Delete or move them first.` (`1 activity`, `that activity` for one) |
| `DELETE /api/themes/{id}` | Activities whose `ThemeIds` contain the id | 409 | `This theme is used by N activities. Remove it from them first.` (`1 activity`, `that activity` for one) |
| `DELETE /api/holidays/{id}` | Activities whose `HolidayIds` contain the id | 409 | `This holiday is used by N activities. Remove it from them first.` (`1 activity`, `that activity` for one) |
| Any of the three, row not used by any Activity | | 204 | |
| Any of the three, id that does not exist | | 204 | (idempotent, as before) |

The count and the delete are two separate storage calls with no lock, so an Activity created between them can still end up pointing at a deleted row. That race is accepted. A storage failure while counting goes through the failure mapping below like any other route (for example a 503 for an outage), and nothing is deleted. Saved Events are unaffected: they keep their own copies of the Game and Activity they selected.

## Comments

| Request | Status |
| --- | --- |
| `GET /api/activities/{id}/comments` | 200 with the Activity's Comments, oldest first by added date (`createdUtc`) then id; 404 for an unknown Activity |
| `POST /api/activities/{id}/comments` | 201 with `Location: /api/activities/{id}/comments/{commentId}`, the `ETag` header and the Comment. The API sets `id`, `activityId` and `createdUtc` and ignores them in the body. 404 for an unknown Activity; 400 for an unknown Event |
| `PUT /api/activities/{id}/comments/{commentId}` | 200 with the Comment. Only the text changes; the added date, the Activity and the Event are kept. 404 when the Comment is missing or belongs to another Activity |
| `DELETE /api/activities/{id}/comments/{commentId}` | 204, idempotent. A Comment of another Activity is also 204 and nothing is deleted |

A Comment in a response carries the same storage keys every other entity's does (`partitionKey`, `rowKey`, `timestamp`, and `eTag` below) beside its own fields `id`, `activityId`, `text`, `createdUtc` and `eventId`; the marker row the removed conversion left (below) is never in a response.

Each Comment is its own row in the `ActivityComments` table (ADR 0001). Deleting an Activity deletes its Comments, and a retried Activity delete after the Activity row is already gone still deletes them. Deleting an Event leaves Comments written from it in place, with their `eventId`. Duplicating an Activity copies none of its Comment rows: a duplicate starts with no Comments, because Comments are rows of their own and belong to the original.

The Activity's old single text and its `PATCH /api/activities/{id}/comments` route were removed in #133; that `PATCH` is no longer a route. An Event's Selection snapshot carries no Comments: Comments are rows of their own, read from the Comment routes, never from a snapshot. An Event stored earlier whose snapshot still has the old text as a `comments` value loads without it (the value is skipped on read), and its next save writes the snapshot without it.

Old texts became Comments (#130) through a one-time conversion that ran at each host start and before Activity `PUT`s until it had finished; it was removed in #247. Stored data was left as it was. The marker row the conversion stored in `ActivityComments` (partition `Migration`, row `activity-notes-v1`) stays, outside the Comment partition, so no Comment list or Activity-delete cascade sees it. An Activity row the API has not written since may still hold the old `Comments` column; the API ignores it, and the next Activity `PUT` replaces the row without it.

## Series and Occurrences (#204)

A Series is its own row in the `Series` table (partition `Series`) with its own eTag (ADR 0002). Its Occurrences are ordinary rows in the `Events` table carrying `seriesId`, `occurrenceKey` (the instant each was generated for, which never changes) and `modified`. A Series' fields are checked in the order of the table above and the first failure wins; the body guard and the failure mapping are the same as every other route's.

| Request | Status |
| --- | --- |
| `GET /api/series` | 200 with every Series |
| `GET /api/series/{id}` | 200 with the Series and its `ETag` header; 404 when unknown |
| `POST /api/series` | Needs an `Idempotency-Key` header (one non-empty GUID in D format; otherwise 400 `Idempotency-Key must be a non-empty GUID in D format.`), which becomes the Series id. 201 with `Location: /api/series/{id}`, the `ETag` header and `{ series, created }`: the Series is stored and its Occurrences for now are created at once (the next 8 weeks, and at least the next one). The Occurrences are worked out before the Series row is written, so a schedule they cannot be made from stores nothing. The same key with the same details answers 200 and creates only the Occurrences still missing (none after a complete first run); different details are 409 `This create key already exists with different details. Reload the Series list and edit the saved Series; do not start another create to retry this save.` and nothing is written. |
| `PUT /api/series/{id}?scope=all` | 200 with `{ series, created, updated, deleted }` and the new `ETag`. The Series is replaced, then every Occurrence that is in the future, not Modified and not played is rewritten in place (name, date, Unique games only) where the new rule still makes its key, deleted where it does not, and the new rule's missing Occurrences are created. An edit never removes an end: on a Series that has one, a body without `end` is 400 `This Series has an end. Send its stored end to keep it, or a new one: an edit cannot remove it.` On a Series a "this and following" edit split, the end can only stay or move earlier, never later or away (400 `This Series was split by a this and following edit, so its end cannot be removed or moved later. Send its stored end, or edit the Series that follows it.`), and no Occurrence the edited rule would make from now on may fall on or after the calendar day the Series that follows it starts: the day of `splitAt`, or of that Series' start when it starts earlier, read at the earliest of the edited, stored and following Series' offsets, so changing the offset cannot move the day. A day, not an instant, because moving the time earlier would otherwise put an Occurrence before the stored end but on the same day as the following Series' first one. 400 `This Series was split by a this and following edit, so it cannot make an Occurrence on or after the day the Series that follows it starts. Send an earlier end, or edit the Series that follows it.` So it never makes Occurrences on the dates of the Series that follows it. On a Series a "this and following" edit started (`splitFrom` set), the start cannot move before `splitFrom`, or before its stored start when that is earlier: 400 `This Series was started by a this and following edit, so its start cannot move before the Occurrence it was split at (or its stored start, if that is earlier). Edit the Series before it instead.` A later start, or another time of day after the split, still works. |
| `PUT /api/series/{id}?scope=following&occurrence={eventId}` | 200 with `{ series, newSeries, created, updated, deleted }`. The Series ends one second before that Occurrence's key (an earlier end it already had is kept), records that key as `splitAt`, and a new Series, the body, starts there and records the same key as its `splitFrom`. Its id is derived from the old Series id and that key, so a repeated request finds it instead of making a second one. The future, unmodified, unplayed Occurrences from that key on move to it: they are deleted and made again under the new Series. Repeating the same request finishes an edit that stopped part-way, even after the chosen Occurrence was deleted (its id is derived from the old Series id and `splitAt`): the leftovers past the old Series' end that are still future, unmodified and unplayed move, and the new Series' missing Occurrences are made; a Modified or played leftover stays with the old Series, and a key cancelled meanwhile is never made again. A split Series cannot be split again at another Occurrence: 400 `This Series was already split by a this and following edit at another Occurrence. Edit the Series that follows it, or this one with scope all.` 400 `Occurrence must name an Occurrence of this Series.` when `occurrence` is missing or names another Series' Event; 400 `This and following from the first Occurrence changes the whole Series: use scope all.` when it names the Series' first Occurrence (or one before its first instant), since the old Series would end before it starts; 400 `Start must be after the Occurrence before the one this change starts from.` when the new start is not after every earlier Occurrence's key. |
| `PUT /api/series/{id}` with another or no `scope` | 400 `Scope must be all or following. Edit one Occurrence through PUT /api/events/{id}.` |
| `DELETE /api/series/{id}?scope=all` | 204. Cancels the Series: its row is deleted, then every Occurrence of it that is in the future and not played. A Series already gone is also 204 and still deletes those Occurrences, so a retried cancel finishes the job. Any other `scope` is 400 `Scope must be all. Cancel one Occurrence through DELETE /api/events/{id}.` |
| `PUT /api/events/{id}` of an Occurrence | The "this occurrence" scope: the Event route as before, and the Occurrence becomes Modified. Any successful `PUT` does this, a save that changes nothing and a roll from the edit dialog included, and from then on no Series edit rewrites that Occurrence. |
| `DELETE /api/events/{id}` of an Occurrence | The cancel-one scope: its key is recorded in its Series' `skipped` list first, then the Event delete runs as before (its metrics row goes with it). A stale `If-Match` is 409 and records nothing. |

An Occurrence is **played** when it has a Winner, at least one Comment written from it (`eventId`), or Event metrics with at least one value; the Comments and Event metrics tables are read through their stores. **Past** means its date is not after now. No Series edit ever rewrites or deletes a past, Modified or played Occurrence, and a Series cancel never deletes a past or played one (a Modified, unplayed future one goes with its Series). After an edit, the edited rule's instants that fall on the calendar date (at the Series' offset) of an Occurrence that stays, or of a cancelled one, are added to `skipped`, so no second Occurrence is made beside one that stays, and a cancelled date stays cancelled when only the time of day changes.

The Occurrence id is the first 16 bytes of the SHA-256 of `series-occurrence:{series id}:{occurrence key as UTC ticks}` (see `SeriesOccurrences.OccurrenceId`), created with the atomic insert, so a retried, overlapping or second run never duplicates or overwrites an Occurrence.

A Series edit and a cancel-one never drop each other's change. A Series `PUT` with no `If-Match`, or with `If-Match: *`, writes conditionally on the version it read; when a cancel is recorded in between, it reads the Series again (with the new `skipped` key) and redoes the edit, up to 5 times, then answers 409. A Series `PUT` whose `If-Match` names a version that is no longer current is 409 and writes nothing. Recording a cancelled key re-reads and retries on a conflict. Each Occurrence a Series edit rewrites or deletes is re-checked for Event metrics first (they live in another table, so the row's eTag does not show them) and written only if its row is unchanged since the edit read it; one that was cancelled, edited by hand or given Event metrics in the meantime is left as it is, nothing is made on its date, and its key is added to the edited (or new) Series' `skipped`, so an Occurrence cancelled during a "this and following" edit does not come back under the new Series. A Comment added in the meantime is not re-checked. Deleting an unplayed Occurrence deletes its Event metrics row only as it was read. A Series edit is several writes on separate rows (ADR 0002): a failure part-way can leave some Occurrences rewritten and others not. Repeating the same request (same scope, same body, and for "this and following" the same `occurrence`) finishes it: an `all` edit deletes the old-rule leftovers and makes the missing Occurrences, and a "this and following" edit is resumed as described above. The daily run only adds missing Occurrences and does not repair a part-done edit. A repeat that carries the first request's `If-Match` gets 409 and must reload first.

The skipped keys (`skipped`: one list, "never make this instant again", holding the cancelled Occurrences' keys and the instants an edit held, as ADR 0002 says) are stored as one JSON value on the Series row and, like an Event's Selections, split over `Skipped`, `Skipped__1`, ... when longer than 30,000 characters. A key is about 28 characters of JSON, so one chunk holds about 1,000 skipped keys, and about 18,000 fit in the 1 MiB entity limit; past that, recording another is refused with 413 `Skipped is too large to store.` before anything is written. A weekly Series would need hundreds of years of cancellations to get there.

## Conflict-safe writes (ETags and If-Match)

Every Game, Theme, Holiday, Activity, Event, Comment and Series carries its Table Storage ETag as the string property `eTag` in the JSON body (lists included), and every single-entity response (GET one, POST, PUT, the Comment `POST` and `PUT`) also sends it as the HTTP `ETag` header. A client may echo it as `If-Match` on `PUT`, `DELETE` and the Comment `PUT` and `DELETE`; the value is passed to storage as given. If-Match is optional, and only the header counts: an `eTag` in a request body is ignored.

| Request | Status |
| --- | --- |
| `PUT` (other than the Event metrics `PUT`, below) with a current `If-Match`, or with none, or with `If-Match: *` | 200, with the new ETag (a Series `PUT` with none or `*` redoes itself when the Series changed while it ran; see Series and Occurrences) |
| `PUT` with a stale `If-Match` | 409 `The request conflicts with the stored data. Reload and try again.`; the row is unchanged |
| `PUT` for a row that was deleted, even between the existence check and the write, with or without `If-Match` | 404; the row is not recreated (updates are never upserts) |
| `DELETE` with a stale `If-Match` | 409; nothing is deleted |
| `DELETE` of a row that does not exist | 204 (idempotent, as before) |
| `PUT /api/activities/{id}/comments/{commentId}` with a stale `If-Match` | 409; the text is unchanged |
| `DELETE /api/activities/{id}/comments/{commentId}` with a stale `If-Match` | 409; the Comment is kept |

Each Comment row has its own eTag, so editing one Comment never makes another Comment or the Activity stale.

An Event's metrics row carries an ETag too, in the body and the `ETag` header. `GET /api/events/{id}/metrics` of an Event with no stored row answers 200 with every field `null`, the Event id, and no `ETag` header. `PUT /api/events/{id}/metrics` is the deliberate exception to "updates are never upserts": it creates the row when none exists. Without `If-Match` it only creates, as an insert, so two first saves cannot overwrite each other.

| `PUT /api/events/{id}/metrics` | Status |
| --- | --- |
| No `If-Match`, no stored row | 200, the row is created, with its ETag |
| No `If-Match`, a row is stored (including one another first save just created) | 409 `The request conflicts with the stored data. Reload and try again.`; the row is unchanged |
| Current `If-Match`, or `If-Match: *`, on a stored row | 200, with the new ETag |
| Stale `If-Match` | 409; the row is unchanged |
| Any `If-Match` (including `*`) with no stored row | 409; nothing is created |
| Unknown Event | 404 |

Deleting an Event also deletes its metrics row, after the Event delete answers 204 (including a retried delete of an Event already gone). A 409 delete deletes neither.

## Event metrics for every Event (the Stats page and the Activity details)

`GET /api/event-metrics` (#136) is the one bulk read behind Activity performance, read by the Stats page and by the Activity details dialog. It takes no body, sends no `ETag` and writes nothing. It answers 200 with a JSON array of `{ eventId, attendees, newAttendees, returningAttendees, amountSpent, likes }`: one item for every Event that has a stored metrics row or at least one Like, the metric fields `null` when not recorded and `likes` the Event's Like count. An Event with neither has no item, which the browser reads as no metrics and 0 Likes. The Like counts come from one pass over the `FeedbackLikes` table that reads only the keys. Like rows are written under the Event id in its hyphenated form, so a partition key that is not a Guid in that form (not a Guid at all, or one in braces or without hyphens) is skipped. Whether each Event still exists is not checked: the browser matches items to its Events list by id and ignores the rest. A storage failure goes through the failure mapping below like every other route (for example a 503 for an outage).

## Long values (chunked properties)

Table Storage limits one string property to 64 KiB of UTF-16, which is 32,768 characters. A complex property (an Event's `Selections`, an Activity's `ThemeIds`/`HolidayIds`) is stored as compact JSON, with non-ASCII text kept as the character rather than a `\uXXXX` escape. When that JSON is longer than 30,000 characters it is split over `Selections`, `Selections__1`, `Selections__2` ... and joined again on read. Five Selections with every field at its cap are about 70,000 characters, so three chunks. The API contract does not change, and a row written before chunking (one property) reads back unchanged.

## Failures after validation (every route)

| Failure | Status | Body | Logged as |
| --- | --- | --- | --- |
| Table Storage conflict (409) or failed `If-Match` precondition (412), other than the event-create idempotency path that the route handles itself | 409 | `The request conflicts with the stored data. Reload and try again.` | Warning |
| A complex property (for example an Event's `Selections`) that would push the row past Table Storage's 1 MiB entity limit or 252 custom properties, even split into chunks; refused before anything is written | 413 | `<Field> is too large to store.` (for example `Selections is too large to store.`) | Warning |
| Entity or property too large for Table Storage (`EntityTooLarge`, `PropertyValueTooLarge`, `RequestBodyTooLarge`, or a 413) | 413 | `The item is too large to store.` | Warning |
| Storage outage or timeout: a `RequestFailedException` with status 500 or above, or status 0 (transport); an `HttpRequestException`; a `TaskCanceledException` that is not the caller's own cancellation; an `AggregateException` made only of these | 503 | `Storage is temporarily unavailable. Try again shortly.` | Error |
| Anything else | 500 | `An unexpected error occurred.` | Error |

When the caller cancels the request, the cancellation is rethrown to the host. It is not turned into a response and it is not logged as a failure.

Every failure is logged through `ILogger<T>` in the Functions class, with the exception and the function name. That output reaches the Functions host log, and Application Insights too when the Function App has it configured. The two unused Application Insights worker packages and the commented-out registration block were removed. Nothing in the worker had used them.
